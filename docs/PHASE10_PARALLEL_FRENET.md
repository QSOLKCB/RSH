# Phase 10 — Parallel Frenet acceleration research

## Goal

Phase 10 begins the second upgrade track in the project roadmap: replacing the
single-invocation full-path GPU recurrence with a separately versioned parallel
prefix construction.

The work is intentionally isolated from both existing geometry surfaces:

- the canonical geometry contract remains `2.0.0` and retains its Python/Rust
  oracle policy;
- the v2.6 research path remains `RSH-FRENET-NUMERICS-V1`, with a sequential
  midpoint update and modified Gram–Schmidt after every step;
- the new parallel surface is `RSH-FRENET-PARALLEL-V1`.

A new contract is required because per-step Gram–Schmidt projection is nonlinear
and cannot be inserted into an associative prefix operation without changing the
algorithm.

## Interval transform

For interval `i`, evaluate curvature and torsion at the interval midpoint and
construct a local rigid transform:

```text
L_i = (R_i, d_i)
```

where:

- `R_i` is the Rodrigues rotation generated by the midpoint Frenet angular
  vector `(tau_i, 0, kappa_i)` over one step;
- `d_i` is the midpoint body tangent rotated over half a step and multiplied by
  `ds`.

Transforms compose in interval order:

```text
(R_a, p_a) ⊗ (R_b, p_b)
  = (R_a R_b, p_a + R_a p_b)
```

This operation is associative in exact arithmetic. Floating-point results still
depend on composition order, so the contract names that order explicitly.

## Deterministic inclusive scan

`hillis-steele-inclusive-se3-v1` uses doubling offsets:

```text
1, 2, 4, 8, ...
```

At pass `k`, output element `i` becomes:

```text
previous[i - offset] ⊗ previous[i]
```

when `i >= offset`; earlier elements are copied unchanged. Each pass reads a
complete immutable source array and writes a distinct target array.

The native f64 reference validates the scan against a sequential fold of the
same local transforms. This proves the scan order implements the declared
composition; it does not assert identity with the v2.6 projected path.

## Rust research crates

```text
crates/rsh-parallel/       f64 interval, scan, path, and shard reference
crates/rsh-parallel-cli/   native run, trace, shard, and CPU timing commands
crates/rsh-parallel-wasm/  raw WASM ABI over the shared Rust implementation
```

The default reference uses 1,025 points and therefore requires 11 doubling
passes. Every report records:

- scan and interval policies;
- frame and centering errors;
- scan-versus-sequential-transform residual;
- ordered shard-merge residual;
- explicit false values for actual parallel hardware execution, distributed
  execution, speedup claims, and geometry-receipt authority.

## Raw WASM ABI

```text
rsh_parallel_abi_version()
rsh_parallel_run(samples, s0, s1,
                 kappa_fraction, tau_floor, tau_amplitude)
rsh_parallel_output_ptr()
rsh_parallel_output_len()
```

The ABI returns the complete f64 path and report. It is the browser correctness
reference for the parallel WGSL scan, not a second canonical geometry runtime.

## WGSL execution

`web/wgsl/frenet_parallel_scan.wgsl` contains four compute entry points:

1. `build_local` constructs all interval transforms in parallel;
2. `scan_step` performs one doubling pass into a ping-pong transform buffer;
3. `capture_centre` records the exact discrete midpoint translation;
4. `emit_path` writes centred position, frame, curvature, and torsion values in
   parallel.

For `N` samples, the adapter executes `ceil(log2(N))` scan passes. Each pass uses
64-thread workgroups. The browser reads back all path components and compares
them with the f64 parallel Rust/WASM payload.

The initial f32 gates are deliberately separate from the sequential path gates:

| Component | Maximum absolute error |
|---|---:|
| Position | `5e-4` |
| Frame | `5e-4` |
| Curvature/torsion | `1e-4` |
| Frame norm | `5e-5` |
| Frame orthogonality | `5e-5` |

These are research gates. They may be tightened only after observations from
multiple adapters and toolchains.

## Benchmark policy

The browser laboratory runs:

```text
2 warm-up iterations
7 measured iterations
median end-to-end timing
```

The WASM timing includes ABI execution, JSON serialization, linear-memory read,
and JSON parsing. The WebGPU timing includes buffer allocation, command encoding,
submission, and complete path readback.

A benchmark sidecar may set `speedup_claim: true` only when:

1. an actual WebGPU adapter executed the scan;
2. every measured run passed all residual gates;
3. the sample count is at least 4,097;
4. the measured GPU median is below the WASM median;
5. the sidecar records all timings, adapter metadata, sample count, scan passes,
   and timing scopes.

Such a statement is an **observed device-and-browser result only**. The sidecar
must also state:

```text
universal_speedup_claim: false
geometry_receipt_authority: false
```

Routine CI does not have a browser GPU and therefore never emits an actual
speedup claim.

## Multi-device and distributed groundwork

`rsh-parallel` can reduce contiguous interval ranges into ordered segment
summaries. A summary contains:

- its exact interval range;
- its local SE(3) reduction;
- a non-authoritative evidence boundary.

The merge function rejects missing, overlapping, or unordered summaries and
checks that their ordered reduction reproduces the full final transform.

This is groundwork, not a distributed runtime. A future implementation will
need:

1. local prefixes inside each shard;
2. an ordered prefix over shard reductions;
3. application of each shard's global prefix to its local path;
4. complete path assembly and centering;
5. device, transport, synchronization, and failure evidence;
6. full residual comparison with the f64 contract.

Browser WebGPU does not promise access to multiple physical devices. Native
multi-GPU or distributed execution therefore requires a separate host adapter
and evidence schema.

```bash

  run --samples 1025 \

  benchmark --samples 16385 --loops 10 \
  --json rsh_parallel_cpu_benchmark.json
```

The native benchmark deliberately reports `speedup_claim: false`; it times the
single-process reference and cannot establish GPU acceleration.

## Scientific and evidence boundary

Parallel composition, real hardware execution, or measured performance does not
promote this contract to geometry authority. The parallel report and benchmark
sidecar prove only declared implementation behaviour and observed numerical
agreement under their profiles.
